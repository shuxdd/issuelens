# IssueLens：证据驱动的开源 Issue 调查系统

## Problem Statement（问题陈述）

开源贡献者接手陌生 Starlette Issue 时，需要在代码、文档、历史 Issue 和提交记录之间反复搜索，难以快速找到相关代码、判断问题机制并形成可核验的调查起点。普通 RAG 问答往往使用最新语料、缺少时间边界和严格评测，容易通过未来修复信息泄漏答案，也无法证明多步 Agent 是否比简单检索真正有效。

项目作者需要在六周内完成一个公开、可复现、可评测的 Agent 工程作品，用于应聘校招 AI 应用或 Agent 工程岗位。作品必须展示数据构建、检索、状态管理、工具权限、失败恢复、可观测性和安全终止能力，而不是只展示框架调用和聊天界面。

## Solution（解决方案）

IssueLens 是面向开源贡献者的证据驱动 Issue 调查系统。系统以版本化的调查案例为输入，在调查时点允许访问的 Starlette 代码、文档、历史 Issue 和提交记录中制定计划、检索证据、提出并验证根因假设，最终生成包含事实、证据引用、不确定性、停止原因和建议调查方向的英文调查报告。

评测严格隔离修复 PR、修复后代码和未来文档。候选补丁和测试仅用于验证根因假设，不构成自动修复承诺。系统通过四组可比较实验、冻结主评测集、稳定性子集和安全终止集证明效果、成本、稳定性与安全边界。

## User Stories（用户故事）

1. 作为开源贡献者，我希望输入一个预置 Starlette Issue，从而快速获得调查入口。
2. 作为开源贡献者，我希望看到系统抽取的版本、环境、错误表现和复现信息，从而确认它正确理解了问题。
3. 作为开源贡献者，我希望系统在信息不足时提出最多三个具体问题，从而知道还需要补充什么。
4. 作为开源贡献者，我希望系统先展示调查计划，从而理解它准备如何缩小问题范围。
5. 作为开源贡献者，我希望系统同时检索代码、测试、文档和历史 Issue，从而避免遗漏不同类型的证据。
6. 作为开源贡献者，我希望每条检索结果包含固定 commit、文件路径和行号，从而能够复查原始内容。
7. 作为开源贡献者，我希望看到关键词检索、语义检索和重排后的候选，从而理解结果为何被选中。
8. 作为开源贡献者，我希望系统区分已确认事实和未经验证的根因假设，从而避免把推测当成结论。
9. 作为开源贡献者，我希望系统最多保留三个根因假设，从而避免无边界发散。
10. 作为开源贡献者，我希望每个关键结论都有允许证据支持，从而能够独立验证报告。
11. 作为开源贡献者，我希望报告标出置信度和未解决问题，从而判断是否可以继续实施修复。
12. 作为开源贡献者，我希望系统在证据不足时明确拒绝下结论，从而避免得到貌似完整但错误的答案。
13. 作为开源贡献者，我希望系统在达到工具或时间预算时安全终止，从而避免无限循环和不可控费用。
14. 作为开源贡献者，我希望系统拒绝越权命令和危险请求，从而不让仓库内容诱导其执行不安全操作。
15. 作为开源贡献者，我希望候选补丁只写入临时工作树，从而不影响真实源码仓库。
16. 作为开源贡献者，我希望候选补丁通过目标测试和相关回归测试验证，从而判断根因假设是否成立。
17. 作为开源贡献者，我希望替代补丁只要满足相同行为就可被接受，从而不必机械复刻原修复 PR。
18. 作为开源维护者，我希望看到结构化调查报告，从而将其作为分诊和人工调查的参考，而非最终维护决策。
19. 作为项目作者，我希望从 GitHub 历史记录恢复 Issue 与 closing PR 的真实关系，从而构造可信案例。
20. 作为项目作者，我希望每个调查案例固定调查时点和仓库快照，从而隔离未来信息。
21. 作为项目作者，我希望自动检测允许证据是否晚于调查时点，从而阻止数据泄漏。
22. 作为项目作者，我希望把修复证据与允许证据物理和逻辑分离，从而避免 Agent 意外读到答案。
23. 作为项目作者，我希望记录案例筛选漏斗和排除原因，从而说明数据集如何形成。
24. 作为项目作者，我希望分别评估根因文件、修复修改文件和测试文件的召回，从而不把不同目标混为一个指标。
25. 作为项目作者，我希望比较仅向量检索、混合检索、重排检索和完整 Agent，从而证明每项复杂度带来的收益。
26. 作为项目作者，我希望前三组使用同一个单轮报告生成器，从而让检索方案之间保持可比。
27. 作为项目作者，我希望完整 Agent 复用最佳检索配置，从而把多步调查带来的增益与检索增益区分开。
28. 作为项目作者，我希望冻结测试集后不再用它调参，从而避免过拟合最终结果。
29. 作为项目作者，我希望对稳定性子集重复运行，从而报告模型随机性带来的结果和成本波动。
30. 作为项目作者，我希望安全终止集与主准确率评测分开，从而不会用本应拒答的案例扭曲准确率。
31. 作为项目作者，我希望确定性指标、人工盲评和 LLM 辅助评分并存，从而避免模型自评成为唯一证据。
32. 作为项目作者，我希望所有实验记录模型、提示词、数据集、评测器和应用版本，从而能够复现实验。
33. 作为项目作者，我希望关闭 Langfuse 后仍可运行离线评测，从而避免第三方平台成为事实来源。
34. 作为项目作者，我希望在 Langfuse 中查看节点、工具、检索、Token、费用和评分，从而快速定位失败环节。
35. 作为项目作者，我希望公开 Demo 只回放固定案例，从而在轻量服务器上控制费用和安全风险。
36. 作为项目作者，我希望 GitHub Actions 自动验证测试、类型、格式、构建、Schema、防泄漏和检索回归，从而防止提交破坏可信度。
37. 作为面试官，我希望从 README、演示视频、实验报告和失败案例中理解系统为何有效，从而判断候选人的真实工程能力。
38. 作为面试官，我希望看到未达标指标和降级决策，从而确认项目作者没有只挑选成功结果。
39. 作为复现者，我希望使用一条 Docker Compose 命令启动核心服务，从而低成本验证项目。
40. 作为复现者，我希望无需 Langfuse 账号也能读取冻结案例并运行离线评测，从而独立审查结论。

## Implementation Decisions（实现决策）

### 产品与领域边界

- 产品正式定义为“证据驱动的 Issue 调查系统”，核心产物是调查报告，不使用“自动修复 Agent”作为主定位。
- 第一版仅支持 Starlette；Typer 只有在 Starlette 清洗后无法形成足量案例时才作为补充仓库评估。
- 主要用户是准备理解、复现或修复 Issue 的开源贡献者，维护者是次要用户，面试官只是作品展示对象。
- 产品界面和调查报告使用英文；项目说明以中文为主，并提供英文摘要。
- 交互模式允许最多三个澄清问题；评测模式不允许外部补充信息。
- 调查终态仅允许 `supported`、`insufficient_evidence`、`budget_exhausted` 和 `unsafe_request`。

### 调查案例与时间切片

- 调查案例由 Issue、调查时点、仓库快照、允许证据和修复证据组成。
- 初始数据协议将 closing PR 的创建时间设为调查时点；仓库快照使用默认分支在该时点之前的最新 commit。
- 允许证据只包含调查时点之前可见的代码、测试、文档、Issue 内容、评论和默认分支提交历史。
- closing PR 的正文、讨论、提交、文件 diff、修复后代码和后来更新的文档均属于修复证据，不得进入 Agent 上下文。
- 如果 Issue 正文曾在调查时点之后编辑且无法恢复当时版本，该案例不得进入主评测集。
- 相关 Issue 系列和同一修复系列必须位于同一数据分组，不能跨开发集与测试集。
- Git 中的版本化 JSON 或 YAML 文件是案例、切分、标注、预注册指标和原始实验结果的权威来源。
- 只发布案例清单、标注、来源引用和重建脚本，不重新分发大规模 GitHub 原文或仓库历史。

### 系统边界与组件

- 后端采用 Python 3.12、FastAPI 和 LangGraph，并使用 `uv` 管理主应用依赖；历史案例测试容器使用与各自快照兼容的 Python 版本。
- 数据存储采用 PostgreSQL 与 pgvector；关键词检索使用 BM25；Reranker 通过可替换接口接入。
- 前端采用 TypeScript、React、Vite 和 `pnpm`，只实现预置案例选择、调查进度、轨迹时间线、报告和证据侧栏。
- API 使用 REST/JSON；调查进度优先使用 Server-Sent Events，并提供轮询降级。
- 模型供应商通过统一适配接口接入；主生成模型走 API，本地只运行 embedding、Reranker 和应用服务。
- 主模型、embedding 和 Reranker 的具体型号通过开发集实验选定，正式评测固定名称、版本、参数和运行日期。
- Langfuse 用于轨迹、成本、评分和实验比较；关闭 Langfuse 后，应用和离线评测仍必须工作。
- 公开 Demo 不实现登录，使用固定案例 ID、IP 级速率限制、全局并发上限和 HTTP 429。
- 公开 Demo 默认回放预生成轨迹，不在线执行补丁测试；实时调查关闭或进入串行队列。
- 所有时间以 UTC 的 ISO 8601 格式持久化。

### 测试接缝

- 调查运行主接缝接收一个版本化调查案例和运行模式，返回调查报告、调查终态、完整事件轨迹及工具、时间和费用统计。
- GitHub、模型、向量库、沙箱、时钟和 Langfuse 均位于调查运行接缝之外，可在测试中替换为固定实现。
- 数据集构建接缝接收固定 GitHub 响应缓存和仓库快照，输出版本化调查案例及筛选报告。
- 除沙箱安全测试外，不直接以单个 LangGraph 节点作为主要测试接口。

### Agent 状态与工具

- 调查状态依次覆盖 Issue 解析、信息充分性判断、计划、检索、证据汇总、根因假设、验证、可选补丁验证、反思或终止、报告输出。
- 关键分支包括信息不足、检索无结果、工具异常、模型结构化输出失败、低置信度、预算耗尽和危险请求。
- 工具限定为 `search_code`、`semantic_search`、`read_file`、`inspect_history`、`run_tests` 和 `submit_patch` 六类。
- 总工具调用不超过 20 次，检索改写最多 2 次，根因假设最多 3 个，补丁尝试最多 2 次，单案例不超过 5 分钟。
- 达到预算时必须保留已确认事实和证据，输出未解决问题与停止原因。
- 仓库内容、Issue、文档和代码注释均视为不可信数据，不能改变系统指令、工具权限或安全策略。

### 补丁验证与安全

- 补丁只写入临时工作树，不修改数据源仓库，不自动创建 GitHub PR。
- 运行容器默认断网，不挂载宿主机密钥或工作区外路径，并限制 CPU、内存、输出和时间。
- 测试命令必须来自调查案例白名单，不允许模型生成任意 Shell 命令执行。
- 原修复 PR 不是唯一正确答案；替代补丁只要解决相同行为、通过目标和相关回归测试且没有越权修改，即可判定成功。
- 公开 Demo 不接受仓库 URL、代码、补丁或命令输入。

### 可比较实验组

- G1 使用仅向量检索，并接入固定的单轮报告生成器。
- G2 使用 BM25 与向量混合检索，并接入与 G1 完全相同的单轮报告生成器。
- G3 使用混合检索加 Reranker，并接入与 G1、G2 完全相同的单轮报告生成器。
- G4 使用 G3 的检索配置和完整多步调查 Agent。
- G1 至 G4 使用相同模型、数据版本和报告 Schema；只有被研究的检索或 Agent 机制可以变化。
- 检索指标比较全部四组；报告质量、根因判定、引用、成本和延迟也在相同报告接口上比较。
- 消融实验分别移除调查计划、Reranker、证据校验、测试反馈和失败反思，且每次只改变一个因素。

### 评测数据与计算口径

- 自动清洗 100–150 条候选，人工复核约 80 条，冻结 30 条主评测案例，其中固定 10 条作为稳定性子集并各运行 3 次。
- 另建 15 条安全终止案例：5 条信息不足、5 条跨仓根因、5 条提示注入或危险请求。
- gold 文件分为 `root_cause_files`、`changed_files` 和 `test_files`；三类分别计算 Recall，预注册的 `Recall@10 ≥ 70%` 指 `root_cause_files`。
- MRR 和 nDCG@10 以人工复核的根因文件相关性等级计算，不能把格式化或顺带修改文件计为根因文件。
- 根因判定采用三级评分：`2` 为机制和代码区域均正确，`1` 为方向正确但机制不完整或范围过宽，`0` 为错误、无证据或使用未来信息；主准确率只将 `2` 计为正确。
- 引用有效率的分母是调查报告中支撑事实和根因结论的全部引用；引用必须位于允许证据内、定位可解析且内容能够支持对应结论才计为有效。先逐报告计算，再对报告做宏平均。
- 无法构建或无法静态分析的案例在冻结前排除并记录原因；冻结后运行失败仍保留在指标分母中。
- 项目作者盲评全部 30 条主评测案例，第二位评审者独立评审预先固定的 10 条子集，并报告一致率、分歧和仲裁。
- LLM Judge 只作为辅助，不替代确定性指标和人工复核。
- 完整 Agent 相比 G1 的“明确提升”定义为：根因正确率至少提高 10 个百分点，且根因文件 Recall@10 或引用有效率中至少一项提高 5 个百分点；同时公开成本与延迟变化。
- 30 条主评测案例各运行一次作为主结果；10 条稳定性子集额外运行两次，报告终态一致率、根因结论一致率、费用和延迟波动。

### 交付与降级

- 六周总 API 预算不超过人民币 300 元。
- 第 1 周完成数据管线和 10 条人工案例；第 2 周完成检索基线和 MVP；第 3 周完成调查状态机；第 4 周冻结评测；第 5 周完成受限补丁验证与界面；第 6 周完成发布材料。
- 第 3 周若根因文件 Recall@10 低于 60%，暂停补丁闭环，优先修复数据、切分、查询构造和检索融合。
- 进度不足时依次削减真实上游贡献、UI 美化、补丁案例数量和在线实时运行，不削减时间切片、防泄漏、检索基线、冻结评测、证据引用和安全终止。
- 若补丁成功率低于 50%，项目与简历仍定位为调查系统，并将补丁验证描述为探索性能力。
- 必须交付开源仓库、一键启动、受控在线 Demo、90 秒视频、中文 README 与英文摘要、架构图、状态机图、数据说明、评测与消融报告、安全威胁模型、失败复盘和面试材料。
- 公开 Demo 固定展示 5 条轨迹：2 条 `supported`、1 条 `insufficient_evidence`、1 条 `budget_exhausted` 和 1 条 `unsafe_request`；至少 1 条 `supported` 展示补丁验证。

## Testing Decisions（测试决策）

### 总体原则

- 好测试只验证可观察行为、领域不变量和安全边界，不锁定 LangGraph 内部节点数量、提示词文本或私有类结构。
- CI 使用固定模型响应、固定 GitHub 缓存和小型仓库快照，确保快速、无费用、无网络依赖和可重复。
- 正式离线评测使用固定的真实模型配置，并与 CI 测试分开，通过手动工作流触发。
- 每次实验必须记录应用 commit、案例版本、调查时点、模型配置、提示词版本、评测器版本和运行日期。

### 调查运行接缝测试

- 使用固定调查案例验证四类调查终态及其停止原因。
- 验证信息不足时，交互模式最多产生三个具体问题，评测模式进入 `insufficient_evidence`。
- 验证每个关键事实或根因结论都有可解析的允许证据引用，否则只能作为未验证假设。
- 验证工具、检索改写、根因假设、补丁尝试和时间预算不会超限。
- 验证工具异常、无效结构化输出和检索无结果会进入规定的降级或安全终止路径。
- 验证关闭 Langfuse 后调查结果与本地事件记录仍可生成。

### 数据集构建接缝测试

- 使用固定 GitHub 响应缓存验证 Issue–PR 关系恢复、候选过滤和幂等构建。
- 验证调查时点晚于允许证据且早于所有修复证据。
- 验证默认分支快照是调查时点之前的最新 commit。
- 验证调查时点后编辑且无法恢复原文的 Issue 被排除。
- 验证同一修复系列不会跨开发集和测试集。
- 验证 Schema、来源 URL、commit、时间和许可元数据完整。
- 人工注入未来证据时，泄漏检查必须失败。

### 检索与评测测试

- 使用同一案例、模型和报告生成器运行 G1、G2 和 G3，仅改变检索配置。
- G4 复用 G3 检索配置，只增加多步调查行为。
- 使用手工可计算的小数据验证 Recall@k、MRR、nDCG、宏平均引用有效率和根因准确率实现。
- 固定小型检索回归集进入 GitHub Actions；全量模型评测只允许手动触发。
- 主评测集冻结后，测试工具必须阻止用同一版本结果覆盖预注册最终运行。
- 稳定性子集必须能关联三次独立运行并计算一致性和成本波动。

### 补丁沙箱测试

- 验证补丁只能写入临时工作树。
- 验证网络、宿主机密钥、工作目录外路径和白名单外命令不可访问。
- 验证超时、CPU、内存和输出限制生效。
- 验证最多两次补丁尝试后停止。
- 验证目标测试和相关回归测试分别记录，不能只凭补丁成功应用判定通过。
- 使用安全终止集覆盖提示注入、路径穿越、命令注入、密钥读取和无限输出。

### 前端与发布测试

- 验证用户可以选择五条预置案例并查看预生成轨迹、报告和证据。
- 验证四类调查终态在界面上具有不同且明确的状态说明。
- 验证无效案例 ID、超限请求和服务不可用时显示可操作错误。
- 验证公开模式不能提交仓库 URL、代码、补丁或 Shell 命令。
- GitHub Actions 运行 Python 单元与集成测试、Ruff、类型检查、前端 lint/build、数据 Schema、防泄漏、Docker Compose 冒烟和小型检索回归。

### 测试先例

- 当前仓库尚无实现代码或现有测试先例；首个实现必须围绕上述两个最高层接缝建立测试结构。
- Starlette 修复 PR 中的行为测试只作为调查案例的修复证据和沙箱目标测试，不复制为 IssueLens 内部实现细节测试。

## Out of Scope（范围外）

- 任意仓库、多仓统一索引和跨仓自动根因调查。
- 自动创建或修改 GitHub Issue、评论、分支和 PR。
- 自动修复成功率承诺。
- 用户提交代码或任意命令的在线执行。
- 多 Agent 群聊、自主角色组织或无界协作。
- 多租户、复杂权限、计费、社交登录和企业账户。
- 模型训练或微调。
- 语音、移动应用和复杂前端设计系统。
- Kubernetes 部署和自研向量数据库。
- 大规模原始 GitHub 内容再分发。
- 将 Langfuse 或 PostgreSQL 作为评测唯一事实来源。
- 将真实上游 PR 合并作为项目完成条件。

## Further Notes（补充说明）

- 权威产品需求见根目录 PRD，领域语言见根目录领域上下文，时间切片和评测数据源决策见两份 ADR；如这些文档变更，本规格必须同步更新。
- 每周必须产生可运行且可人工验证的增量。实现顺序以数据可信、检索评测、调查状态机、可观测性、发布材料、补丁验证、UI 美化为优先级。
- 第一个可交付结果不是聊天页面，而是 10 条可审查调查案例、泄漏检查命令和筛选漏斗。
- 项目作者必须能解释核心模块的输入、输出、不变量、替代方案和失败案例；无法解释的 AI 生成代码不计入成果。
- 每周末进行一次约 20 分钟的模拟面试复盘，记录本周的技术决策和失败实验。
- 后续可使用工单拆分技能把本规格分解为独立实现任务；工单应从数据可行性和时间切片管线开始，而不是从前端开始。
